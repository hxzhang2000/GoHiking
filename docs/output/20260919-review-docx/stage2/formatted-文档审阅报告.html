二、已核实的高危问题（7 条，建议动工前必修）

每条均已由我本人回读原文行号确认，非转述 agent 的判断。

H-1 【DEV】记录期分批落库与保存期全量重插互相矛盾 —— 同一批点会写两遍

  • 位置：DEV-DESIGN.md L658 vs L659 / L666–671
  • 问题：L658 规定「记录中写轨迹点：每批 10 点 / 每 5 秒一次事务 insertBatch(points)」，即点在记录期间就已落库；而 L659 与 L666–671 的 saveFinishedTrip(trip, points, markers) 在保存时又把内存中的 points 全量重插一遍。同一批点写两次：主键冲突，或（若无主键约束）距离与统计翻倍。
  • 佐证：L1550「丢弃 → 删除已落库的轨迹点」也印证记录期点已在库中。
  • 建议：二选一并写死——① 记录期只写内存/临时表，保存时一次性入库（则 L658 应改为「写内存缓冲」，且崩溃恢复会丢最近一批点，需评估）；② 记录期分批入库、保存时只补 trip 行与 marker（saveFinishedTrip 去掉 points 重插，改为 update trip + 关联校验）。倾向 ②，与崩溃恢复语义（L1548 沿用 tripId）自洽。

H-2 【DEV】ksp { arg("room.schemaLocation", ...) } 写在 android {} 块内 —— 照抄直接编译失败

  • 位置：DEV-DESIGN.md L1612（处于 L1560 android { 与 L1614 } 之间）
  • 问题：KSP 扩展注册在项目级，android 扩展上没有 ksp 访问器。本文档自称「可直接照写」，照抄会 Unresolved reference: ksp，且 schema 不导出会连带 §3.1 的「schema 提交仓库 + MigrationTestHelper 迁移测试」整条链路失效。
  • 建议：ksp { arg(...) } 移到与 android {} 平级的顶层块。

H-3 【DEV】含「每场记录」状态的 AltitudeFuser / AlertEngine 被 @Singleton 注入 RecordingSession —— 第二场记录沿用第一场的基准

  • 位置：DEV-DESIGN.md L1397–1401（构造注入 altitudeFuser、alertEngine）vs §4.3（altRef 标定窗口「开始后前 10 秒」）、§4.9（distanceAcc、三个 lastXxxMarkM 基准）
  • 问题：RecordingSession 是 @Singleton（冻结决策），直接持有这两个有逐场可变状态的协作者。第二场记录会继承上一场的 altRef、气压基准、距离/海拔打点基准 —— 首场记录一切正常，测试极难发现。
  • 建议：改为注入工厂（AltitudeFuserFactory / AlertEngineFactory），start() 时新建实例；或显式定义强制 reset() 生命周期并纳入 §6.6 恢复流程。同时修正 L1548「重建 RecordingSession」的措辞（单例无法重建，应为 rebind(tripId)），并为两者补 restore(state) 接口（恢复需回灌基准，否则恢复后提醒会重复触发）。

H-4 【DEV】「逐段运动时长必须落库」没有任何承载结构 —— 冻结决策在数据层落不了地

  • 位置：DEV-DESIGN.md L1236 vs L400–421（recording_state 表）
  • 问题：§4.12 明文「必须由 RecordingSession 在暂停时逐段记下时长并随记录落库」，TripStatsCalculator.compute 也要求入参 movingSecBySegment；但 recording_state 只有总量 accumulatedPausedMs，全篇无逐段时长字段、无 segment 表，§9.3 的 D-01~D-03 也没登记。
  • 影响：保存时可用内存值，但崩溃恢复后中断前各段运动时长永久丢失，平均速度/配速（C3 裁定的口径）只能退化成「首尾点差」。
  • 建议：recording_state 增 movingSecBySegmentJson TEXT（逐段序列化），或新增段时长表；崩溃恢复路径同步补「读回逐段时长」。

H-5 【DEV/PRD】导出 JSON 的三个字段在 Room 表中无来源列 —— 「导出与导入对称」接不住

  • 位置：PRD L1270–1279（media_ref 表）、L1241–1248（planned_route 表）vs PRD L1542/1544（JSON media[].fileName、media[].note）、L1495（plannedRoute.source: "AUTO"）
  • 问题：media_ref 只有 uri 没有 fileName/note（content:// URI 解析不出原始文件名）；planned_route 没有 source 列（只有 waypoint 级 source，语义不等价）。导出实现时要么临时加列（Room 版本 +1），要么导出缺字段破坏 7.3 schema。DEV §9.3 也未为此登记 D-xx。
  • 建议：media_ref 补 fileName、note，planned_route 补 source；或在 7.3 声明该字段由 waypoint source 派生。

H-6 【PRD/跨文档】里程碑枚举漏掉约 15 条 P0 —— 按 §11 走查会漏验

  • 位置：PRD L2152–2216（M0–M4）对照 L709–727、L863–871、L1124
  • 问题（已逐条核对优先级）：
  • M1 只列 F-REC-01~10、15~18、50~54、60~66、70~75，漏掉同为 P0 的 F-REC-30~33（登顶点）、F-REC-36/37（上下山分界）、F-REC-40~42（手动打点） 共 9 条；
  • F-HIS-26（上山/下山分段统计）、F-HIS-27（标记列表）、F-HIS-30（操作栏）、F-HIS-33/34（平均速度/配速口径） 5 条 P0 无处安放（M1 只到 F-HIS-01~10、20~22，M4 只到 23~25）；
  • M3 导入只列 F-IO-20~35、40~44，漏掉 P0 的 F-IO-36（settings.json 默认不导入）。
  • 影响：PRD 是「测试验收基线」，DEV §9.4 DoD 又只要求 §9.1 的域级映射逐条可追 —— 按现文走查，这批 P0 会被漏验，v1.0 可能带着「无标记列表、无上下山统计」的详情页通过验收。
  • 建议：用脚本反扫 M0–M4 的编号并集与「全部 P0」承诺的差集，补齐区间；并在 M1/M3/M4 加兜底句「域内未列出的 P0 默认归属本里程碑」。

H-7 【PRD】F-ALERT-29「计入本次记录的爬升/下降统计」与双累加器口径冲突

  • 位置：PRD L979 vs L888
  • 问题：L888 明确「累计爬升用阈值法自己的累加器（3m/10m），与海拔打点累加器（100m）完全独立，不要合并」；而 L979 说标记「计入本次记录的爬升/下降统计」。照字面实现会把打点值再累加进统计，造成重复累计。
  • 建议：改为「标记及其累计量在标记列表中可见，不参与统计累加（统计口径见 6.5.2）」。
