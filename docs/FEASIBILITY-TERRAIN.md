| 功能 | 技术难度 | 预估工作量 | 建议版本 | 备注 |
| --- | --- | --- | --- | --- |

| **坡度着色**（Slope） | ★★☆☆☆ | 3–5 天 | v1.3（如需可并入 v1.2） | 与山体阴影共用 90% 代码 |

**一句话总结**：前三项是「给平面地图加一层有信息的贴图」，难度可控；第四项是「换掉整个地图渲染引擎」，属于架构决策，不是功能开发。

## 1. 前置事实：高德 SDK 到底给了什么

### 1.1 高德地图 Android SDK 的能力清单

| 能力 | 是否支持 | 说明 |
| --- | --- | --- |
| 底图（标准 / 卫星 / 夜间） | ✅ | |
| 覆盖物 Marker / Polyline / Polygon | ✅ | 矢量绘制，可交互 |
| GroundOverlay（地面贴图） | ✅ | 贴一张图到指定经纬度矩形 |
| **TileOverlay（自定义瓦片图层）** | ✅ | **本方案的关键入口**——可以叠加自己生成的瓦片 |
| 视角倾斜（tilt）/ 旋转（bearing） | ✅ | 可以做俯视角度，**但地面是平的** |
| 建筑体块（3D 城市） | ❌ | 高德 App 有，**开放平台 SDK 不提供** |
| **地形高度（terrain）** | ❌ | **没有**。地面永远是 0 海拔的平面 |
| **DEM / 高程数据服务** | ❌ | 高德开放平台**未提供公开的高程瓦片或 DEM 接口** |

### 1.2 关键结论

> **高德 SDK 没有地形渲染管线。** 它不像 MapLibre GL / Mapbox GL 那样有 `raster-dem` 数据源 + `terrain` 属性 + `hillshade` / `color-relief` 图层这类一等公民支持。

这决定了：

- **等高线 / 坡度 / 山体阴影** → 只能走「**离线生成瓦片 + TileOverlay 贴上去**」这条路，本质是给地图加一层**有信息量的半透明贴图**。做得到，效果也好，但它是**平面着色**，不是几何体。
- **真 3D 地形** → 高德 SDK 无解。要么换引擎，要么自己写 OpenGL 渲染。

## 2. DEM 数据从哪来

等高线、坡度、山体阴影**三者都需要同一份东西：DEM（数字高程模型）栅格数据**。这是整条链路的地基。

### 2.1 候选数据源

| 数据源 | 分辨率 | 覆盖 | 获取方式 | 评价 |
| --- | --- | --- | --- | --- |
| **AWS Terrain Tiles**（terrarium 编码） | 30m | 全球 | 公开 S3，免 Key | ⭐ 最省事，但**境外服务，国内访问可能不稳，无 SLA** |
| **Mapbox Terrain-RGB** | 30m | 全球 | 需 Token，有免费额度 | 质量好，但绑定 Mapbox 账号与配额 |
| **Copernicus DEM GLO-30** | 30m | 全球 | 免费下载原始栅格 | ⭐ 质量优于 SRTM，**适合自建** |
| **Copernicus DEM GLO-90** | 90m | 全球 | 公开聚合 API（如 Open-Meteo）可直接查询，或免费下载 | ⭐ **v1.0 路径 A 的实际首选**（免 Key、国内可达）；但 90 m 分辨率对陡峭山峰**系统性低估**（见下方实测说明） |
| **SRTM 1 arc-second** | 30m | 全球（60°N~56°S） | 免费下载 | 经典方案，山区有数据空洞 |
| **ALOS AW3D30** | 30m | 全球 | 免费下载 | 日本 JAXA，质量好 |
| **国内 12.5m DEM** | 12.5m | 中国 | 社区公开分享 | 精度最高，但来源需自行核实合规性 |

> **90 m 级 DEM 的系统性低估（2026-09-19 实测）**：90 m 分辨率 DEM（GLO-90 / SRTM 90m 同级）在陡峭山峰处**系统性低估**海拔——泰山玉皇顶实测 1532.7 m 报 1479 m（低 54 m）、黄山光明顶实测 1860 m 报 1725 m（低 135 m）。这是**偏差而非随机误差**，重复查询不会变准；直接影响等高线海拔标注与线路爬升估算的可信度，界面必须标注「估算」（PRD `F-PLAN-46`），v1.2 切换 GLO-30 后低估会收窄但不会消失。

### 2.2 两种取数路线

**路线 ①：直接调外部瓦片服务（快，但不可控）**

```
App → 请求 AWS/Mapbox 的 terrain-RGB 瓦片 → 本地解码 → 生成叠加瓦片
```

- 优点：零运维，几天就能跑通
- 缺点：依赖境外服务、无 SLA、随时可能变、有速率限制
- **风险**：爬山场景经常没信号，这条路在离线时直接失效

**路线 ②：自建 DEM 瓦片服务（慢，但可控）** ⭐ 推荐

```
下载 Copernicus/SRTM 原始 DEM
  → 离线预处理：投影到 Web Mercator + GCJ-02 纠偏
  → 切片成 terrarium / terrain-RGB 瓦片
  → 部署到自己的对象存储或 CDN
  → App 按需拉取 + 本地缓存
```

- 优点：可控、可缓存、离线友好、无境外依赖
- 缺点：需要一次性搭管线，有存储成本
- **注意**：这是**后端工程**，不是 App 功能。要么自己搭，要么依赖公共服务

> **决策点**：如果接受「地形图层只在有网时可见」，可以先用路线 ① 快速验证；如果要保证爬山时（通常无信号）也能看到等高线，**必须走路线 ②，并且做瓦片预下载**。

## 3. 最大的技术风险：坐标系

这是整个方案里最容易翻车、也最容易被低估的地方。

| 数据 | 坐标系 |
| --- | --- |
| DEM 原始数据（SRTM / Copernicus / AWS Tiles） | **WGS-84** |
| 高德地图底图 | **GCJ-02** |

**直接把 WGS-84 的 DEM 生成等高线贴到高德地图上，等高线会整体偏移几百米**——你看到的山脊线会比真实山脊偏出一整条山沟。这在爬山场景里是致命的，等于图层没用。

### 为什么不能简单平移

GCJ-02 对 WGS-84 的偏移**不是固定向量**，而是随经纬度非线性变化的（大致几百米量级，方向和大小都变）。所以不能加个固定 offset 了事。

### 可行解法

| 方案 | 做法 | 成本 | 评价 |
| --- | --- | --- | --- |
| **A. 逐像素纠偏（离线）** | 对每个 DEM 像素做 WGS-84 → GCJ-02 映射，重采样成新栅格 | 一次性计算量大，但离线做 | ⭐ **推荐**。在预处理阶段解决，App 端零成本 |
| B. 整片瓦片近似平移 | 对每张瓦片算中心点偏移，整片平移 | 便宜 | ❌ 误差仍有几十米，山脊对不齐 |
| C. App 端反向转换 | 把高德坐标转回 WGS-84 再取 DEM | App 端有开销 | 只在交互式取高程时用，不适合整层渲染 |

**结论**：在**离线预处理阶段**做逐像素纠偏，是唯一干净的解法。这进一步说明**自建管线（路线 ②）是正解**——如果依赖外部瓦片服务，你没法在中间插一步纠偏。

### 验证方法

上线前必须做一件事：**挑一座你熟悉的山，把生成的等高线和实际地形对照**。推荐用有明确标志物的位置（山脊、鞍部、水库岸线）检查对齐情况。对不齐就说明纠偏逻辑有问题，不要往下做。

## 4. 分项技术分析

### 4.1 等高线（Contour Lines）

**技术链**

```
DEM 栅格
  → marching squares 算法提取等值线
  → 折线抽稀（Douglas-Peucker）
  → 两种渲染路径：
     (a) 服务端栅格化成 PNG 瓦片  ← 推荐
     (b) 转成高德 Polyline 矢量绘制
```

**难点排序**

| 难点 | 严重度 | 说明 |
| --- | --- | --- |
| 坐标系纠偏 | 🔴 高 | 见第 3 节，做错整个图层作废 |
| DEM 数据源稳定性 | 🟠 中 | 境外服务不可控，建议自建 |
| 瓦片索引对齐 | 🟠 中 | 需确认高德 TileOverlay 用的是标准 Web Mercator XYZ 编号，**必须实测** |
| 折线点数量爆炸 | 🟡 低 | z=15 单瓦片可能出几千个点，用栅格瓦片而非 Polyline 即可规避 |
| 等高距选择 | 🟡 低 | 山区 50m 或 100m，平原 10m，需按缩放级别动态调整 |

**渲染方式怎么选**

| 方式 | 优点 | 缺点 |
| --- | --- | --- |
| **栅格瓦片**（服务端出 PNG） | 性能好，点数无所谓 | 不能交互（点不动、不能高亮某条线） |
| **Polyline 矢量** | 可交互、可高亮、可标注海拔 | 点数一多就卡，z>14 基本不可用 |

**建议**：主用栅格瓦片；只对「用户点击的那条等高线」按需用 Polyline 高亮并显示海拔值。两者结合。

**难度：★★★☆☆** — 算法本身是教科书内容（marching squares 半天能写完），**真正的难度全在数据和坐标系上**。

---

### 4.2 坡度着色（Slope Coloring）

**技术链**

```
DEM 栅格
  → 3×3 窗口计算坡度（Horn 算法，与 GDAL 默认一致）
  → 按角度映射到色带
  → 半透明叠加
```

**难点排序**

| 难点 | 严重度 | 说明 |
| --- | --- | --- |
| 算法本身 | 🟢 极低 | Horn 算法十几行代码 |
| **色带与透明度设计** | 🟠 中 | 图层是半透明的，压太重看不清底下的路网，压太轻看不出坡度 |
| 阈值分级 | 🟡 低 | 户外习惯：<15° 缓、15–25° 中、25–35° 陡、>35° 极陡 |

**关键优势**：**坡度与山体阴影共用同一套 DEM 管线和 90% 的计算逻辑**。等高线管线建好后，坡度几乎是「多写一个渲染函数」的量。

**难度：★★☆☆☆** — 前提是 DEM 管线已经存在。如果从零开始，成本要算在等高线那一项里。

### 4.3 山体阴影（Hillshade）

> 原始需求里没提，但**强烈建议加**，因为它的性价比是全套里最高的。

**做法**：由 DEM 计算坡度和坡向，套一个光照模型（模拟太阳从西北 45° 照射），输出灰度明暗图，半透明叠在底图上。

**为什么值得做**

- 一张图就把「哪儿是山脊、哪儿是山沟」表达清楚了，立体感立刻出来
- 这是所有专业户外地图的标配（Gaia GPS、CalTopo、两步路的地形图都靠它）
- 算法与坡度共用大部分计算，增量成本极低

**难度：★★☆☆☆** — 全套里最简单的一项。

---

### 4.4 真 3D 地形（Terrain）

**这是唯一一项「在高德 SDK 上做不到」的功能。**

#### 为什么做不到

真 3D 地形需要渲染管线具备三个条件：

1. 能读取 DEM 并做**顶点位移**（把平面网格按高程抬起来）
2. 能做**透视投影**（山体在旋转/倾斜时有视差）
3. 能做**遮挡剔除**（近处的山挡住远处的山）

高德 SDK 一个都不给。它的 tilt 视角只是**把一张平面图斜过来看**，山不会立起来。

#### 三条可能的实现路径

| 路径 | 做法 | 难度 | 工作量 | 代价 |
| --- | --- | --- | --- | --- |
| **伪 3D** | 高德 tilt 视角 + 山体阴影 + 预渲染的透视地形图 | ★★★☆☆ | 1–2 周 | 视觉上像，但**没有视差**——转动视角时山不动，一眼假 |
| **换引擎** | 改用 MapLibre GL Native（原生支持 `raster-dem` + `terrain` + `hillshade`） | ★★★★☆ | 3–4 周 | **放弃高德**：国内地图合规、POI 数据、路径规划、坐标系全部要重做 |
| **自绘** | OpenGL ES / Vulkan 自己写地形网格渲染器，高德只当底图或不用 | ★★★★★ | 6–10 周 | 等于造一个小型地形渲染引擎，维护成本长期存在 |

#### 换引擎这件事的真实成本

MapLibre GL 本身很香——加个 `raster-dem` 数据源、设置 `terrain` 属性，3D 地形就出来了，代码量极小。但代价是：

| 要重做的东西 | 说明 |
| --- | --- |
| 地图底图 | 不能用高德瓦片，要么自建，要么用 OSM（**国内合规风险**） |
| POI 搜索 | 高德 POI 搜索能力作废 |
| **路径规划** | 计划线路功能的地基没了，要换其他服务商 |
| 坐标系 | 又要处理一遍 GCJ-02 问题，而且这次是在别人的引擎里 |
| 合规 | 在中国大陆发布地图类应用，底图数据来源有明确要求，需要认真评估 |

> **结论**：换引擎不是「加个 3D 功能」，是「重做地图层」。这个决策的影响面覆盖 PRD 的 6.1 / 6.2 / 6.4 三个功能域，**必须在动工前独立评估，不能顺手做**。

## 6. 建议的落地节奏

### 过渡策略：v1.0 先用第三方高程 API，v1.2 再切自建管线

PRD 6.1 定义了三级高程路径（A 第三方公开服务 → B 自建 DEM 瓦片 → C 本地缓存）。落地节奏是**先用路径 A 撑起 v1.0 的 F-MAP-06 长按查海拔与 6.2.3 线路爬升估算，待 v1.2 自建管线（路径 B）就绪后切换**：

| 阶段 | 高程数据源 | 说明 |
| --- | --- | --- |
| v1.0（当前目标） | 路径 A：公开高程 API——**首选 Open-Meteo（GLO-90，90 m）**；OpenTopoData / Open-Elevation 为备选（OpenTopoData 需按数据集逐个探测可用性，`aster30m` 实测超时；实测记录见 DEV-DESIGN §4.10） | 按采样点批量查询 + 本地缓存；调用带**指数退避重试与超时熔断**；零运维、几天跑通；**离线时不可用，海拔显示「—」**（符合 6.1 降级规则） |
| v1.2（阶段一完成后） | 路径 B：自建 Copernicus GLO-30 瓦片 + 本地缓存 | 离线可用、可控；高程查询缓存 Key 与 DEV-DESIGN §3.1.1 一致、**按坐标计**；切换后因数据源分辨率不同（90 m → 30 m），**旧的高程查询缓存必须失效重建** |

**切换触发条件**（满足其一即切换）：

1. 阶段一最后一项「验证对齐」通过——用一座熟悉的山对照等高线与实际山脊，确认纠偏正确（go / no-go 关卡，见第 7 节验证 2）
2. v1.2 开发排期启动，且自建管线已部署到对象存储

**切换注意事项**：

- App 端保留**统一的高程查询接口**（对上层只暴露「查坐标 → 海拔」），路径 A/B 只是该接口的不同实现，切换只改实现不碰调用方
- v1.0 的第三方缓存与自建路径的**高程查询缓存共用坐标键**（与 DEV-DESIGN §3.1.1 的坐标 5 位小数键一致），但切换后因数据源分辨率不同，**缓存值必须整体失效重建**，不得新旧混用；瓦片层规格（XYZ 编号 vs 坐标块）不对齐，两条路径的瓦片不互用
- **用户可见的高程数值切换后会整体变化**：90 m → 30 m 后系统性低估收窄，同一线路的爬升 / 最高海拔估算会**变小**；「估算」标注（`F-PLAN-46`）与统计口径不变，需在发布说明中提示用户数值差异属预期
- 若 v1.2 排期延后，路径 A 可持续支撑，无强制失效风险——切换不是死线，是能力升级

### 阶段一：v1.2 — 山体阴影 + 等高线（3–4 周）

1. 搭建离线 DEM 管线：下载 Copernicus GLO-30 → Web Mercator 投影 → **GCJ-02 逐像素纠偏** → 切片 → 存对象存储
2. App 端：`TileOverlay` + 自定义 `TileProvider`，支持图层开关、透明度调节、瓦片本地缓存
3. **验证对齐**：拿一座熟悉的山实测，等高线与实际山脊是否重合（**这是 go / no-go 的关卡**）
4. 加山体阴影（与等高线共用管线）

### 阶段二：v1.3 — 坡度着色 + 预下载（1–2 周）

5. 加坡度色带图层
6. 加**瓦片预下载**：出发前把目标区域的 DEM 瓦片下载到本地，解决爬山时无信号的问题

### 阶段三：v2.0 — 真 3D 地形（需独立评估）

7. 评估是否切换到 MapLibre GL
8. 如果决定换，那是一次**架构迁移**，不是功能迭代——建议单独立项

## 7. 动工前必须验证的三件事

| # | 待验证 | 方法 | 不通过的后果 |
| --- | --- | --- | --- |
| 1 | **高德 TileOverlay 的瓦片索引是否为标准 Web Mercator XYZ** | 用一张自制的、带明显标记的测试瓦片贴上去，看位置对不对 | 整个贴图方案不成立，需要自建编号映射 |
| 2 | **GCJ-02 纠偏后等高线与真实地形是否对齐** | 拿一座熟悉的山，对比山脊线、鞍部、水库岸线 | 图层偏移几百米，等于没用 |
| 3 | **多层叠加的性能** | 等高线 + 阴影 + 坡度三层同时开，在低端机上测帧率 | 需要降级为「同时最多开两层」 |
