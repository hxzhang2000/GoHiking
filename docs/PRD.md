## 1. 产品概述

### 1.1 一句话定义

**「去爬山」是一款以地图为核心，面向登山/徒步爱好者的「计划 — 记录 — 回顾」一体化 Android 应用。**

用户在出门前用它在真实地图上规划**去程 + 返程**两条线路；爬山过程中用它记录**完整轨迹、海拔与步数**，并在关键节点收到**距离/海拔语音提醒**；回家后可以把手机里散落的**照片和视频按拍摄位置聚合到地图上**，配合运动数据一起回顾，并把整条轨迹导出成**一个开放格式的文件**。

### 1.2 为什么做这个产品

| 现状 | 问题 |
| --- | --- |
| 悦跑圈 / Keep / 咕咚 | 以跑步、骑行为主，登山场景的**海拔爬升统计**、**登顶点标记**、**返程规划**支持薄弱 |
| 两步路 / 六只脚 | 户外功能强，但界面复杂、商业化重、**数据导出封闭**，导出的文件缺字段 |
| 手机自带相册 | 照片只能按时间浏览，**无法和轨迹关联**，爬山照片散落各处 |
| 各类运动 App | 数据在云端，用户**无法完整拿回**自己的原始数据 |

### 1.3 目标用户

| 用户画像 | 典型特征 | 核心诉求 |
| --- | --- | --- |
| 周末爬山党（主力） | 每月 1–4 次，多为成熟路线，用手机记录 | 简单好用、自动记录、有照片回顾 |
| 硬核徒步者 | 频繁走野线、需要规划返程、看重数据完整性 | 精准海拔、完整轨迹、可导出、可标记 |
| 数据党 / 开发者 | 想把轨迹导入其他工具分析 | 开放的导出格式、字段齐全 |

### 1.4 核心价值主张

1. **计划**：在地图上**点选或搜索**起点和终点，自动推荐多条线路；没路可推就手动打途经点。**去程和返程分开规划**。
2. **记录**：红色实时轨迹 + 海拔打点 + 步数统计，支持暂停/恢复、登顶点标记。
3. **提醒**：距离提醒和海拔提醒可配置，支持语音播报，且**在轨迹上留下标记**。
4. **回顾**：手机里的照片/视频按位置聚合到地图上，与运动记录一起看。
5. **开放**：单条记录一键导出**一个 JSON 文件**（含轨迹、海拔、标记、提醒、统计全量数据），全量备份导出**一个 ZIP**；**导出与导入必须对称**——导出的文件必须能原样导回来。

### 1.5 产品原则

| 原则 | 含义 |
| --- | --- |
| 数据属于用户 | 本地优先存储，无账号体系，随时完整导出，无锁定 |
| 记录零干扰 | 一次点击开始，锁屏/切后台不影响；耗电可控 |
| 符合直觉 | 交互参考主流运动 App（Keep / 咕咚 / 两步路）的操作习惯，不发明新交互 |
| 不炫技 | 地图是第一界面，数据是第二界面，没有多余的动画和装饰 |

## 2. 术语表

| 术语 | 英文 / 字段名 | 定义 |
| --- | --- | --- |
| 计划线路 | `PlannedRoute` | 出发前规划的线路，在地图上以**蓝色线**显示 |
| 去程 / 登山路径 | `outbound` | 计划线路中的上山段，从起点到登顶点 |
| 返程 / 返回路径 | `return` | 计划线路中的下山段，从登顶点回到终点 |
| 实际路线 / 轨迹 | `Track` | 记录过程中采集的真实路径，在地图上以**红色线**显示 |
| 轨迹点 | `TrackPoint` | 一次定位采样，含经纬度、海拔、时间、精度、速度 |
| 路段 | `Segment` | 被「暂停」或**定位信号长时间丢失**切分开的一段连续轨迹。暂停一次、或信号丢失后恢复，即新增一个 segment（见 9.6） |
| 标记 | `Marker` | 用户或系统在轨迹上留下的语义点（登顶点、提醒点、手动标注） |
| 登顶点 | `summit` | 用户手动标记的线路最高/折返点，用**小红旗**图标表示 |
| 提醒点 | `alert` | 距离或海拔提醒触发时自动打下的标记。**海拔提醒点同时也是海拔记录点** |
| 聚合点 | `Cluster` | 地图上把相近的多张照片/视频合并显示的圆形气泡 |
| 坐标系 | CRS | 本产品涉及 **WGS-84**（GPS 原始）与 **GCJ-02**（高德/国测局）两套 |

### 4.2 高德 SDK 选型

| 能力 | 使用的 SDK / 接口 | 用途 |
| --- | --- | --- |
| 地图显示 | 高德地图 SDK（3D 地图） | 底图、缩放、Marker、Polyline、聚合 |

| POI 输入提示 | 高德搜索 SDK（`InputtipsQuery` + `Inputtips.requestInputtipsAsyn()`） | 搜索框边输入边联想（见 6.2.1） |
| 底图 POI 点击 | 高德地图 SDK（`AMap.setOnPOIClickListener` → `onPOIClick(Poi)`） | 点击地图上已有 POI 直接设为起点/终点（见 6.2.1） |

**关于路径规划模式的说明**：高德开放平台提供**步行、骑行、驾车、公交**四类路径规划，**没有专门的「登山/徒步」模式**。本产品采用**步行路径规划**作为默认引擎（登山本质是步行），并在推荐结果上叠加自己的**海拔爬升评估**来排序（见 6.2.3）。

**Key 申请与配置要求**：

- 在高德开放平台创建应用，为 Android 平台申请 Key
- 绑定项：**应用包名** + **SHA1 签名指纹**（Debug 与 Release 各申请一个 Key）
- Key 通过 `AndroidManifest.xml` 的 `<meta-data android:name="com.amap.api.v2.apikey">` 注入
- **开源注意**：仓库中**不得提交真实 Key**。做法：Key 写入 `local.properties` 或 `keystore.properties`（已在 `.gitignore` 中排除），通过 Gradle `manifestPlaceholders` 注入；仓库只保留 `local.properties.example` 模板
- 隐私合规：必须在**用户同意隐私政策之后**再调用 `AMapLocationClient.updatePrivacyShow/updatePrivacyAgree`，否则 SDK 不工作

### 4.3 坐标系问题（关键技术点，必须严格遵守）

这是本产品最容易出错、也最影响体验的地方。

| 数据来源 | 坐标系 |
| --- | --- |
| 手机 GPS 芯片原始输出 | WGS-84 |
| 高德定位 SDK / 高德地图 SDK | GCJ-02（火星坐标系） |
| 高德 POI 搜索 / 输入提示的返回结果 | GCJ-02（**无需转换**，与内部存储一致） |
| 照片 EXIF / MediaStore 中的 GPS | WGS-84 |
| GPX 标准文件 | WGS-84 |

**处理规则**：

1. **内部存储统一使用 GCJ-02**：因为地图显示是高德（GCJ-02），记录时用高德定位 SDK 直接得到 GCJ-02，无需转换，保证红线贴合地图道路。
2. **照片/视频的 GPS 是 WGS-84**，显示到高德地图上**必须转为 GCJ-02**，否则会产生**非线性偏移**（实测 40.9~686.3 m，随位置非线性变化，不可用固定偏移量修正；论证见 [FEASIBILITY-TERRAIN.md](./FEASIBILITY-TERRAIN.md) §3）。
3. **导出时明确标注坐标系**，并提供转换选项：
   - 默认导出 `GCJ-02`（与国内主流 App 一致）
   - 可选导出 `WGS-84`（用于导入国际工具如 Garmin、Strava、Google Earth）
4. 每个轨迹点在导出文件中的 `crs` 字段必须与实际坐标一致，**不允许含糊**。
5. 转换算法需包含**中国大陆范围判定**（境外坐标不做偏移），并有单元测试覆盖。

### 4.4 海拔数据策略

> **前提：气压计是可选硬件，不是所有 Android 手机都有。** 绝不能假设设备有气压计。

Android 提供了 `SensorManager.TYPE_PRESSURE` 这个 API 常量，但硬件由厂商决定是否焊上去。实际情况：

| 机型档位 | 气压计 |
| --- | --- |
| 旗舰机（三星 S/Note 系列、Pixel 全系、华为 Mate/P 系列、小米数字旗舰、一加旗舰等） | 多数**有** |
| 中端机 | 部分有 |
| 入门机 / 千元机 | 基本**没有** |
| 同一型号不同批次 | 可能不同 |

**能力检测**（启动记录时执行一次，结果写入本次记录）：

```kotlin
val hasBarometer = sensorManager.getDefaultSensor(Sensor.TYPE_PRESSURE) != null
```

#### 4.4.1 有气压计：融合方案（首选）

气压计相对变化精度高（约 ±0.1~1m），但绝对高度受天气影响；GPS 海拔绝对精度差（±10~30m）但长期无系统偏差。两者互补：

| 来源 | 特性 | 使用方式 |
| --- | --- | --- |
| 气压计 `TYPE_PRESSURE` | 相对变化精度高，绝对值受天气影响 | **主数据源**，用于计算爬升/下降 |
| GPS 海拔 | 绝对精度差，但长期无系统偏差 | **基准校准**，校准气压计零点 |

**算法**：

1. 记录开始时，取前 10 秒 GPS 海拔的中位数作为基准 `altRef`，同时记录此刻气压 `pRef`
2. 之后每次采样用 `SensorManager.getAltitude(SEA_LEVEL_STANDARD_ATMOSPHERE, pressure)` 得到气压高度 `altBaro`
3. 输出海拔 `alt = altRef + (altBaro - altBaroRef)`
4. 每 60 秒用 GPS 海拔对 `altRef` 做一次缓慢漂移修正（低通滤波，避免跳变）
5. 入库前经**滑动中值滤波**抑制毛刺

标记 `altitudeSource = BAROMETER_FUSED`

#### 4.4.2 无气压计：GPS 增强方案（降级）

GPS 海拔噪声大，直接用于「每 100m 打点」会频繁误触发。降级方案必须叠加以下**五道防线**：

| 防线 | 做法 | 目的 |
| --- | --- | --- |
| ① 中值滤波 | 滑动窗口 9 点取中值 | 去掉单点跳变 |
| ② 垂直精度门控 | `Location.getVerticalAccuracyMeters() > 20m` 的点**不参与海拔累计** | 剔除劣质解 |
| ③ 持续确认 | 海拔变化需**连续稳定 10 秒**才确认触发 | 过滤瞬时漂移 |
| ④ 提高阈值下限 | 无气压计时，海拔阈值**下限从 10m 提到 30m** | 让噪声远离触发线 |
| ⑤ MSL 海拔优先 | Android 14+（API 34）优先用 `Location.getMslAltitudeMeters()`，比椭球高更接近真实海拔 | 提升绝对值准确度 |

标记 `altitudeSource = GPS_ONLY`

**精度预期（必须对用户诚实）**：

| 指标 | 有气压计 | 无气压计 |
| --- | --- | --- |
| 单点海拔绝对误差 | ±5~10m | ±15~30m |
| 累计爬升误差 | ±3% 以内 | ±10~15% |
| 能否支撑 100m 打点 | ✅ 可靠 | ⚠️ 可用，但建议阈值 ≥ 30m |

#### 4.4.3 无气压计时的产品降级要求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-REC-60 | 启动记录时检测气压计，检测结果写入本次记录 | P0 |
| F-REC-61 | 检测到无气压计时，记录界面海拔数值旁显示「GPS 估算」角标 | P0 |
| F-REC-62 | 首次在无气压计设备上开始记录时弹一次说明：「本机无气压计，海拔为 GPS 估算，精度较低。建议将海拔提醒阈值设为 30 米以上。」 | P0 |
| F-REC-63 | 无气压计时，海拔提醒阈值下限自动从 10m 调整为 30m | P0 |
| F-REC-64 | 提供**手动海拔校准**：用户可输入当前已知海拔（山顶标高牌、地图标注等），据此校正后续读数 | P1 |
| F-REC-65 | 导出文件中通过 `altitudeSource` 字段标注本次记录的海拔来源 | P0 |
| F-REC-66 | 详情页海拔曲线在 GPS 估算模式下显示「精度较低」提示 | P1 |

#### 4.4.4 兜底原则

**无论有没有气压计，都不影响核心功能**：

- 轨迹记录、距离、时长、步数、照片聚合、导出——全部照常
- 海拔字段照样有值，只是精度不同、来源不同
- 唯一受影响的是**海拔提醒的精度**和**爬升统计的准确性**，通过上面的降级策略把影响压到最小

**爬升/下降统计**：两种模式下都采用**阈值法**——只有连续的海拔变化超过阈值（有气压计 **3m** / 无气压计 **10m**）才计入累计爬升/下降，避免噪声累积出虚假爬升。

### 4.5 计步策略

#### 4.5.1 硬件事实

| 传感器 | API | 覆盖率 | 说明 |
| --- | --- | --- | --- |
| `TYPE_STEP_COUNTER` | 19+ | **绝大多数手机有**，但不保证 | 累计步数（自开机）。**不要求专用硬件**——很多设备用加速度计 + 软件算法实现 |
| `TYPE_STEP_DETECTOR` | 19+ | 与 counter 基本同步 | 每检测到一步发一个事件，不累计 |
| `TYPE_ACCELEROMETER` | 3+ | **几乎所有设备都有** | 可作为兜底数据源 |

**不保证有计步器的设备**：平板、部分低端机 / Android Go 设备、部分定制 ROM、部分无 Google 服务的机型。

检测方式与气压计一致——`getDefaultSensor()` 返回 `null` 即为不支持。需 `ACTIVITY_RECOGNITION` 运行时权限（Android 10+）。

#### 4.5.2 关于第三方数据源（重要结论，不要重复调研）

> 常被问到：能不能读**微信运动 / 华为运动健康 / 小米运动健康**的步数？**答案是基本不能。**

| 来源 | 能否读取 | 结论 |
| --- | --- | --- |
| **微信运动** | ❌ 不提供任何第三方 API。小程序有 `wx.getWeRunData()`，但那只在微信生态内、且要用户授权，原生 App 拿不到 | **不可行** |
| **华为运动健康** | ⚠️ 有 Health Kit，但需 HMS Core + **华为设备** + 在华为开发者联盟申请读步数权限（审核严格，个人开发者基本拿不到） | **不可行**（对开源项目） |
| **小米运动健康** | ❌ 无公开的第三方读步数 API | **不可行** |
| **Health Connect**（Android 官方健康数据平台） | ✅ 可读其他 App 写入的步数 | ⚠️ 国内 ROM 大多未预装、也无数据源，**不能作主力**；可作为 v1.1 的可选数据源 |
| **无障碍服务读界面** | ⚠️ 技术上能做 | ❌ **明确不做**：违反 Google Play 政策、界面改版即失效、需用户开无障碍权限（体验极差） |

**结论：第三方健康 App 的步数拿不到，不要在这上面投入任何工作量。** 兜底靠加速度计自研算法。

#### 4.5.3 四级降级策略

| 优先级 | 数据源 | 触发条件 | 精度 | 额外耗电 |
| --- | --- | --- | --- | --- |
| ① | `TYPE_STEP_COUNTER` | 传感器存在 + 权限已授予 | 高 | 极低（低功耗协处理器常开） |
| ② | `TYPE_STEP_DETECTOR` | 有 detector 但无 counter | 高 | 极低 |
| ③ | **加速度计自研算法** | 无计步传感器，但加速度计可用 | 中 | **中高**（需持续采样 + 跑算法） |
| ④ | 显示「—」+ 手动补录 | 以上全部不可用 | — | — |

#### 4.5.4 各级实现要点

**①② 系统计步传感器**：记录开始时读一次基准值 `stepAtStart`，实时步数 = 当前值 − `stepAtStart`。暂停记录期间不计步。

**③ 加速度计自研算法**（仅在前两级不可用时启用）：

- 采样率 50Hz（无需更高，更高只增加耗电）
- 三轴合加速度 → 低通滤波（去重力分量）→ 带通滤波（**0.5–3 Hz**，对应正常步频）
- 峰值检测 + 自适应阈值 + **最小步间隔 250ms**（防抖）
- 需要 20–30 步的**预热期**做阈值标定，预热期内的步数不计
- **必须提示用户耗电增加**，并提供关闭开关

**④ 手动补录**：记录结束后允许用户手动填写步数。

#### 4.5.5 已知坑

| 坑 | 说明 | 处理 |
| --- | --- | --- |
| 记录中设备重启 | `TYPE_STEP_COUNTER` 归零，基准失效，步数会算成负数 | 检测到计数器回退即判定为重启，标记该段步数不可用并提示 |
| 长时间不重启 | 32 位浮点累计，精度随时间下降 | 记录时长 > 6 小时时提示精度可能下降 |
| 手机不在身上 | 计的是**设备**的步数，不是**人**的步数 | 无法解决，详情页标注「设备步数」 |
| 别人拿着手机走 | 同上 | 同上 |
| 步数不是核心指标 | 本产品核心是轨迹、海拔、距离 | **不为步数引入重方案**（厂商 SDK、无障碍服务一律不做） |

**高程数据来源（重要，不要想当然）**

> **高德开放平台不提供公开的高程 / DEM 接口。** 高德地图 SDK 也没有地形高度（terrain）能力——地面永远是 0 海拔的平面。因此所有「按坐标查海拔」的需求（`F-MAP-06`、6.2.3 的线路爬升评估）都必须**由我们自己解决高程数据源**，不能指望高德。

| 路径 | 做法 | 取舍 |
| --- | --- | --- |
| **A. 第三方公开高程服务**（v1.0 起步） | 调用 OpenTopoData / Open-Elevation 之类的公开高程 API，按采样点批量查询，结果落本地缓存 | 零运维、几天跑通；但**境外服务、无 SLA、需网络**，离线时不可用 |
| **B. 自建 DEM 瓦片**（正解） | 下载 Copernicus GLO-30 / SRTM 原始 DEM → 离线做 GCJ-02 逐像素纠偏 → 切片 → 自建对象存储 → App 端按需拉取 + 本地缓存 | 可控、可缓存、离线友好；但需要一次性搭后端管线，见 [FEASIBILITY-TERRAIN.md](./FEASIBILITY-TERRAIN.md) 第 2 节 |
| **C. 本地 DEM 缓存 + 双线性插值** | 出发前把目标区域的 DEM 瓦片预下载，App 端直接插值取高程 | 爬山时（常年无信号）唯一可行的方案 |

**降级规则**：

- 高程数据不可用（无网且无缓存）时，**只显示经纬度，海拔显示「—」**，并给出原因提示；**不允许编造数值，也不允许沿用上一个点的海拔**
- 计划线路的爬升 / 最高海拔是 **DEM 估算值**，界面上必须标注「估算」，不得与记录时的实测爬升混为一谈（对应需求 `F-PLAN-46`，见 6.2.3）
- DEM 估算值**不写入** `altitudeSource` 字段——该字段只描述**记录**时的实测海拔来源（气压计 / GPS），见 7.3

**交互说明**

- 地图默认倾斜角 0°、俯仰 0°，保持 2D 平面视角，便于观察线路
- 所有覆盖物（Polyline / Marker）在缩放时保持线宽视觉一致（使用 `width` 属性而非屏幕像素）

### 6.2 计划线路（F-PLAN）

**目标**：出发前在真实地图上规划好「怎么上去、怎么下来」，存成一条计划线路，爬山时可以看到蓝线做参照。

#### 6.2.1 入口与基本流程

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-PLAN-01 | 首页地图提供「计划线路」入口 | P0 |
| F-PLAN-02 | 进入计划模式后，地图进入选点状态 | P0 |
| F-PLAN-03 | 用户在地图上点击（或长按）选定**起点** | P0 |
| F-PLAN-04 | 用户在地图上点击（或长按）选定**终点** | P0 |
| F-PLAN-05 | **搜索选点**：起点 / 终点都可通过搜索框输入地名选择（输入联想 + 高德 POI 搜索），**离线时不可用并降级到地图点选** | P0 |
| F-PLAN-06 | 起点/终点选定后可拖动调整位置 | P1 |
| F-PLAN-07 | 提供「以当前位置为起点」快捷按钮 | P0 |
| F-PLAN-08 | **点选底图 POI**：点击地图上已有的兴趣点标记（山名、景区、停车场、公交站等），弹出气泡可直接「设为起点 / 设为终点」 | P1 |
| F-PLAN-09 | **搜不到的兜底**：POI 搜索无结果时提示未找到，并提供「换个城市搜」建议与一键切换到地图点选的入口 | P1 |

**选点方式总览**——起点和终点都支持以下四种方式，用户可任选：

| 方式 | 适用 | 依赖 |
| --- | --- | --- |
| ① 地图点选（点击 / 长按任意位置） | 任何位置，包括野山、POI 数据里不存在的地方 | **无需网络** |
| ② 搜索选点（输入地名） | 知道山名 / 登山口 / 停车场等名称 | **需网络**（高德 POI 搜索） |
| ③ 点选底图 POI | 地图上已经标出来的兴趣点 | 需网络加载底图；且**只有底图自带 POI 有回调** |
| ④ 当前位置 | 从「我现在站的地方」出发 | 需定位权限与 GPS |

> **① 是唯一不依赖网络和数据覆盖的方式，必须永远可用。** ②③④ 是「更快的方式」，不是「唯一的方式」——任何时候都不能让用户卡在选点这一步。

**搜索选点的实现要点（容易踩坑的地方）**

高德给了三个配合使用的接口：

| 接口 | 用途 |
| --- | --- |
| `InputtipsQuery(keyword, city)` + `Inputtips.requestInputtipsAsyn()` | 输入联想，边打字边给候选词 |
| `PoiSearch.Query(keyword, category, city)` + `PoiSearch(context, query).searchPOIAsyn()` | 关键词检索，回调 `onPoiSearched` 返回 `PoiItem` 列表 |
| `PoiSearch.setBound(new SearchBound(中心点, 半径米))` | 周边检索。**登山场景建议默认用它**——以地图视野中心为圆心搜周边，比搜全国准得多 |

三个必须处理的细节：

1. **输入提示返回的 `Tip` 有三种状态，不能一律当 POI 用**
   - `getPoiID()` 为空 且 `getPoint()` 为空 → **不是真实 POI**（可能只是个词），要拿这个词再发一次关键词搜索
   - `getPoiID()` 非空 且 `getPoint()` 为空 → 是**公交线路名**，本产品不处理，直接过滤掉
   - `getPoiID()` 非空 且 `getPoint()` 非空 → 真实 POI，可直接定位并选中
2. **城市参数**：`PoiSearch.Query` 第三个参数传空串代表全国搜索，但涉及多城市时只会返回**建议城市**。默认取「地图视野中心所在城市」并提供切换入口；无结果时用 `result.getSearchSuggestionCitys()` 提示用户换城市
3. **响应码**：`rCode == 1000` 才算成功，其余一律按失败处理并给出可读提示（不许弹「搜索失败」四个字）

**点选底图 POI 的覆盖度限制（必须知道）**

`AMap.setOnPOIClickListener` 的回调 `onPOIClick(Poi poi)` 提供 `getName()` / `getCoordinate()` / `getPoiId()`，但**只对底图上已经渲染出来的 POI 生效**——`Poi` 类的定义就是「底图上的一个自带 Poi 点」。

- 城市里 POI 密集，体验很好；**山区、乡村 POI 稀疏，缩放级别不够时可能一个都点不到**
- 因此 `F-PLAN-08` 定级 P1，且**绝不能作为唯一选点方式**
- **需实测**：选点状态下点击 POI 时 `OnMapClickListener` 是否同时触发——若同时触发，会出现「点 POI 却选到了旁边空白点」的 Bug（列入 M0 验证项）

> **实现说明（2026-09-19 已查证到 API 层；「能不能真的返回 3 条差异明显的线路」仍须实测）**
>
> 本节原写的「高德步行规划单次只返回一条最优结果」**不成立**。经反编译高德 SDK 字节码 + 核对官方文档，**步行多备选是官方原生能力**，共有三条可用路径：
>
> | 路径 | 接口 | 查证结果 |
> | --- | --- | --- |
> | **① 算路 SDK V2（首选）** | `RouteSearchV2.WalkRouteQuery.setAlternativeRoute(int)`，取值 `RouteSearchV2.AlternativeRoute.ALTERNATIVE_ROUTE_ONE/TWO/THREE` | **已确认存在**（`ALTERNATIVE_ROUTE_THREE` 即「要三条」），与 Web API 的取值语义完全对应 |
> | ② 算路 SDK V1 | `RouteSearch.WalkRouteQuery(fromAndTo, RouteSearch.WALK_MULTI_PATH)`，`WALK_MULTI_PATH` 与 `WALK_DEFAULT` 并列 | **已确认存在**（两个构造签名 `(FromAndTo)` 与 `(FromAndTo, int)` 也都在） |
> | ③ 步行 Web API | `GET /v5/direction/walking` 的 `alternative_route`：1=第一条 / 2=前两条 / **3=三条**，不传则一条 | **官方文档明确列出**（注意：**v3 的 `/v3/direction/walking` 没有这个参数**，只有 v5 有） |
>
> 另外导航 SDK 侧也已确认：`TravelStrategy` 枚举有 `SINGLE` / `MULTIPLE` 两个值，`AMapNavi.calculateWalkRoute(..., TravelStrategy)`、`getNaviPaths()`、`setMultipleRouteNaviMode(boolean)` 均存在（官方注明「并非所有路线均支持多路径规划」）。
>
> **结论**：① 为首选（应用内直接调 SDK，不额外引入网络入口与 Key 配额）；② 为同 SDK 的退化路径；③ 仅在 SDK 路径实测不可用时考虑。
> 下面「构造不同的途经点组合」的做法**降级为最后的兜底**，不再是主策略——它本质是在补一个并不存在的缺陷，还会额外消耗配额、产出用户无法理解的线路。
>
> **仍未确定的一点**（必须真机/实跑才能定）：山区、无路网区域下**是否真能返回 3 条差异明显**的方案，还是会把同一条线路返回三遍。若差异不足，仍需与途经点构造法混合使用。选型判定规则见 `docs/DEV-DESIGN.md` §4.8.1。
>
> 无论最终采用哪种方式，**「自动规划失败必须降级到手动打点」这条兜底不变**（见 6.2.4）。

#### 6.2.3 线路评估指标

每条推荐线路需给出：

| 指标 | 来源 |
| --- | --- |
| 总距离 | 路径规划返回 |
| 预计耗时 | 距离 ÷ 3.5 km/h（登山平均速度，可按用户配速调整） |
| **累计爬升** | 沿线路按固定间距采样高程点，用与 4.4 节相同的**阈值法**计算（DEM 估算噪声比传感器大，阈值按 10m 起） |
| 最高海拔 | 采样点最大值 |
| 难度评级 | 由「距离 + 爬升」综合计算，**存枚举值、渲染时本地化**：<br>`EASY`（<5km 且 <300m）<br>`MODERATE`（<10km 且 <800m）<br>`HARD`（<15km 且 <1500m）<br>`CHALLENGING`（超出上述） |

> **难度边界值归属**：上表各档均为**严格不等号**——恰好 5 km / 300 m / 10 km / 800 m / 15 km / 1500 m 时不满足本档条件，归入下一档。

> **难度为什么必须存枚举**：如果直接把「中等」写进数据库和导出文件，用户切到英文后这条记录会残留中文。枚举值（`MODERATE`）是**协议**，不翻译；「中等 / Moderate」是**文案**，走资源文件按当前语言渲染（见 9.7.4）。

> 高程数据**不来自高德**——高德没有公开的高程 / DEM 接口（见 6.1「高程数据来源」）。做法是沿线路按固定间距采样坐标点，经高程数据源批量查询后本地缓存，避免重复请求。**爬升与最高海拔均为 DEM 估算值，界面必须标注「估算」**，不得与记录时的实测爬升混为一谈。

**需求**

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-PLAN-46 | 计划线路的**累计爬升**与**最高海拔**均为高程数据源的估算值，界面在这两项数值旁**必须标注「估算」**（例：「累计爬升 约 820 m（估算）」）；**不得与记录页的实测爬升并列展示而不作区分**；该估算值也不写入 `altitudeSource` 字段 | P1 |

> **为什么必须标注（2026-09-19 实测依据）**：公开 DEM 的空间分辨率有限，在**陡峭山峰处会系统性低估**——这是**偏差而非随机误差，多测几次不会变准**。实测：泰山玉皇顶 **1532.7 m** 实测 vs SRTM 90 m 报 **1479 m**（低 54 m）；黄山光明顶 **1860 m** vs 报 **1725 m**（低 135 m）。若不标注，用户会把自己「计划爬升」与「记录爬升」的差额当成 Bug。技术细节与应对见 [docs/DEV-DESIGN.md](./DEV-DESIGN.md) §4.10。

### 6.3 登山记录（F-REC）

#### 6.3.1 记录状态机

```
        ┌─────────────────────────────────────────────┐
        │                                             │
   [空闲 IDLE] ──开始记录──▶ [记录中 RECORDING] ⇄ [已暂停 PAUSED]
        ▲                        │                      │
        │                        └────── 停止记录 ──────┘
        │                                   │
        └────────── 保存 / 丢弃 ◀── [已停止 STOPPED]
```

| 状态 | 说明 |
| --- | --- |
| `IDLE` | 未记录，首页地图可自由浏览 |
| `RECORDING` | 正在采集定位、海拔、步数；计时器运行 |
| `PAUSED` | 暂停采集，计时器暂停（暂停时长单独统计）；**当前 segment 结束** |
| `STOPPED` | 记录结束，等待用户保存或丢弃 |
| `SAVED` / `DISCARDED` | 用户做出选择：保存 → 落库为 `FINISHED`；丢弃 → 不落库 |

> **「会话状态」与「持久化状态」是两件事（极易混淆，必须分清）**
>
> - 上表是**会话状态机**，描述本次记录过程中 App 的界面状态。其中 `IDLE` / `STOPPED` / `SAVED` / `DISCARDED` **都不落库**
> - `trip.status`（见 7.1）是**持久化状态**，**只取 `RECORDING` / `PAUSED` / `FINISHED` 三个值**
> - 映射关系：会话进入 `RECORDING` / `PAUSED` 时同步写 `trip.status`；用户选择保存 → `trip.status = FINISHED`；用户选择丢弃 → **删除该 `trip` 行及其轨迹点、标记，库里不留痕迹**
> - **只有 `trip.status = 'FINISHED'` 的记录出现在运动记录列表与所有汇总统计中**（`F-HIS-01/04`）。`RECORDING` / `PAUSED` 的行属于「未结束会话」，仅供崩溃恢复使用（`F-REC-09`），**不得出现在列表里**，也不计入统计
> - 会话停在 `STOPPED`（已停止、未保存）时进程被杀：重启后**不按 `RECORDING` 恢复计时**，而是直接弹出保存确认（`F-REC-07`），避免把「已停止」期间的时间算进时长

#### 6.3.7 轨迹采集策略

| 项目 | 策略 |
| --- | --- |
| 采样频率 | 记录中 **1 秒 1 次**（可通过「高精度 / 省电」模式切换为 3 秒 1 次） |
| 最小位移过滤 | 位移 < 3m 的点不入库（但仍在内存中参与速度计算），避免静止时产生海量重复点 |
| 精度过滤 | `accuracy > 50m` 的点标记为低质量，参与绘制但**不参与距离与爬升统计** |
| 速度过滤 | 速度 > 30 km/h 视为异常（乘车/定位漂移），**不参与距离统计** |
| 抽稀 | 入库时保留原始点；绘制时按缩放级别做 Douglas-Peucker 抽稀，避免万点卡顿 |

**统计口径定义（必须严格按此实现）**

同一条轨迹的数据会出现在「记录列表 / 详情页概览 / 图表 / 分段表 / 导出文件」五处。口径不一致就会出现「一个距离有五个值」的问题。以下口径为**唯一标准**：

| 指标 | 口径 | 说明 |
| --- | --- | --- |
| 总距离 `distanceM` | 各 `segment` 内相邻**有效点**距离之和 | 剔除 `quality != 0` 的点、位移 < 3m 的点、速度 > 30km/h 的点（见 6.3.7） |
| 总时长 `durationSec` | 记录开始到结束的墙钟时间 | **含暂停** |
| 运动时长 `movingDurationSec` | `durationSec − pausedDurationSec` | **不含暂停** |
| 平均速度 `avgSpeedMps` | `distanceM / movingDurationSec` | **分母用运动时长，不用总时长**；`movingDurationSec < 1s` 时该值为 `null` |
| 最高速度 `maxSpeedMps` | 逐点瞬时速度的最大值 | 仅统计 `quality == 0` 的点 |
| 平均配速 `avgPaceSecPerKm` | `movingDurationSec / (distanceM / 1000)` | `distanceM < 50m` 时无意义：界面显示「—」，导出写 `null` |
| 最高 / 最低海拔 | 有效点海拔的极值 | 仅统计 `quality == 0` 的点 |
| 累计爬升 / 下降 | 阈值法（见 4.4.4），阈值 3m（有气压计）/ 10m（无气压计） | 与「海拔打点」用的是**两个独立累加器**（见 `F-ALERT-20 ~ 29`），不要合并 |
| 步数 `steps` | 见 4.5 四级降级 | 完全不可用时为 `-1` |
| 卡路里 `caloriesKcal` | 见下方公式 | **估算值**，界面必须标注 |

**卡路里估算公式（v1）**

```
kcal = Σ（ MET_seg × 体重kg × 该段运动秒数 / 3600 ）

MET_seg 按该段净海拔变化斜率判定：
  上坡（斜率 > +3%）  MET = 7.0
  下坡（斜率 < −3%）  MET = 4.0
  其他（平地）        MET = 4.5
```

| 规则 | 说明 |
| --- | --- |
| 体重来源 | 设置项「通用 › 体重」，默认 **65 kg**（`F-SET-06`） |
| 段粒度 | 公式中的「该段」= 每 **100 m 运动距离**一个窗口（尾段不足 100 m 并入前一窗口）；窗口内净海拔变化 ÷ 窗口距离 = 该段斜率 |
| 累计范围 | **只累计运动时段**，不含暂停 |
| 样本下限 | `movingDurationSec < 60s` 时不出卡路里（样本太短、估算无意义），界面显示「—」，导出写 `null` |
| 标注义务 | 界面卡路里数值旁必须标注「估算」；**不得宣称「精确消耗」** |
| 版本可追溯 | 导出/备份包的 `README.txt` 中写明所用公式版本（当前为 v1）与参数，便于下游复现 |

> **这是估算模型，不是医学级能量代谢计算**。目的只是给用户一个量级参考，参数（MET 值、斜率阈值）允许在后续版本按实测数据调整，但**调整必须升公式版本号并写入 README.txt**。

**分段表（`F-HIS-25`）切分规则**

| 表 | 切分依据 | 段内用时口径 |
| --- | --- | --- |
| `byKilometer` | 按**累计运动距离**每满 1 km 切一段 | 段内**运动**时间（跳过跨暂停的时间差） |
| `byAltitudeGain` | 按**累计爬升**（阈值法）每满 100 m 切一段 | 同上 |

- 两个表**独立计算**：同一段轨迹可能同时出现在两个表里，互不影响
- 尾段不足 1 km（或不足 100 m 爬升）时**照常列出**，标注实际距离 / 实际爬升
- **暂停期间的时间不计入任何一段**
- 每段 `paceSecPerKm = 段内运动秒数 / (段距离 / 1000)`；段距离 < 50 m 时写 `null`

### 6.8 数据导出 / 导入（F-IO）

> **核心原则：数据完全属于用户。能导出成什么，就必须能导回来——导出与导入是一对，必须对称。**
>
> 一个只有导出没有导入的 App，本质上是「数据单程票」。本产品要求：**导出的文件必须能被自己完整还原**，并且换设备后能一键恢复。

#### 6.8.1 两种粒度

| 粒度 | 格式 | 用途 | 典型体积 |
| --- | --- | --- | --- |
| **单条记录** | `.json` | 分享给朋友、单条迁移、二次分析（jq / pandas） | 0.5–3 MB |
| **全量备份** | `.zip` | 换手机、整体备份、灾难恢复、批量迁移 | 10–500 MB |

两者的关系：**ZIP 里装的就是 JSON**。单条 JSON 是基本单元，ZIP 是多条 JSON + 清单 + 设置的容器。这样一套解析器就能同时处理两种输入。

#### 6.8.7 验收标准

- 导出 42 条记录为 ZIP，在另一台设备导入，**记录数、轨迹点数、标记数、统计数值全部一致**
- 导出的单条 JSON 用 `jq` 能解析出全部轨迹点与标记
- 同一个 ZIP 导入两次，第二次全部被跳过（**幂等**）
- 手工构造一个含 `../../evil.txt` 路径的 ZIP，导入被拒绝且**不写出任何文件**
- 导入 `schemaVersion: "2.0"` 的文件，给出「请升级 App」提示而**不是崩溃**
- 导入 100 条记录中途取消，再次导入不产生重复
- 导出 3 小时记录的 ZIP 体积在 5 MB 以内（不含媒体文件）
- 导入 1000 条记录（约 1 GB ZIP）时 App 不 OOM，进度可感知

- `track_point(tripId, segmentIndex, seq)`
- `track_point(tripId, timestamp)`
- `marker(tripId, type)`

**容量估算**：1 秒 1 点、3 小时 = 约 10800 点，单点约 80 字节 → 单次记录约 0.9 MB。100 次记录约 90 MB，可接受。

### 7.2 导出格式选择：为什么用 JSON

| 候选格式 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **JSON** | 可嵌套、可扩展、可读、几乎所有语言原生支持、能承载任意自定义字段 | 体积略大（无压缩时比二进制大 3–5 倍） | ✅ **主格式** |
| GPX 1.1 | 户外/运动生态标准，Garmin、Strava、Google Earth 都认 | 是 XML，字段表达能力弱：**无法表达提醒点、计划线路、照片引用、步数、暂停分段**等自定义语义；写扩展需自定义命名空间，兼容性差 | ✅ **兼容格式（可选导出）** |
| FIT | 体积小，Garmin 原生 | 二进制，需要专有 SDK，调试困难 | ❌ 不做 |
| KML | Google Earth 友好 | 不适合承载运动统计数据 | ❌ 不做 |
| CSV | 表格工具友好 | 无法表达层级结构（标记、计划线路） | ⚠️ v1.1 可加 |

**结论**：**以 JSON 为唯一主存储/主导出格式**，GPX 作为可选的「互操作导出」。

理由展开：

1. 本产品的数据是**层级化**的（记录 → 路段 → 轨迹点 → 标记 / 提醒 / 照片），JSON 天然适合，GPX 强行表达会很别扭。
2. 产品会持续演进（加新标记类型、加新统计字段），JSON 加字段不破坏旧解析；GPX 加字段要改命名空间。
3. 用户要求「导出成单独一个文件」——JSON 单文件即可自包含全部信息。
4. 用户是开发者，JSON 便于二次分析（pandas / jq / 自写脚本）。
5. 体积问题可通过**可选 gzip 压缩**缓解（`.json.gz`），或对轨迹点使用**数组化的紧凑写法**（见下）。

**紧凑写法优化**（可选，减少 40%+ 体积）：轨迹点用「字段名数组 + 值数组」的方式，避免每个点重复 key。

#### 7.2.1 GPX 1.1 映射规则

**GPX 恒用 WGS-84**（标准要求，也是 Garmin / Strava / Google Earth 的预期）。因此 GPX 导出**与「导出坐标系」设置无关**（`F-IO-14`）。这一点极易写错：若沿用 GCJ-02 导出，文件在 Garmin 上会整体错位几十至几百米（GCJ-02 偏移为**非线性**，实测 40.9~686.3 m），而**用户无从察觉**——他不会想到是坐标系问题。

| 本产品数据 | GPX 1.1 落点 |
| --- | --- |
| 记录名称、开始时间 | `<metadata><name>` / `<metadata><time>` |
| 每个 `segment` | 一个 `<trkseg>`（**保住暂停断开语义，绝不合并**） |
| 每个轨迹点 | `<trkpt lat lon>` + `<ele>`（海拔） + `<time>` |
| 每个 `marker` | 一个 `<wpt>`：`<type>` 写**枚举原文**（如 `ALERT_ASCENT`，**不翻译**，见 9.7.4）、`<name>` 写按当前语言本地化的展示文本、`<desc>` 写用户备注 |
| 计划线路 | **不导出** |

**明确丢弃、且必须在导出完成时告知用户的内容**（`F-IO-16`）：

- 步数、卡路里
- `altitudeSource` / `stepSource`（海拔与步数的来源标识）
- 提醒设置（`alertSettings`）
- 计划线路、照片引用
- 分段表（`splits`）与各项统计汇总

理由：GPX 1.1 没有承载这些语义的元素；强行写 `<extensions>` 需要自定义命名空间，反而降低第三方工具兼容性。**宁可明确丢弃并告知，也不要用非标准扩展让文件在别的工具里解析失败。**

| `altitudeSource` | **必填**。海拔来源：`BAROMETER_FUSED` / `GPS_ONLY` / `MANUAL_CALIBRATED`。下游分析海拔数据前必须先看这个字段——`GPS_ONLY` 的爬升统计误差可达 ±10~15% |
| `stepSource` | **必填**。步数来源：`SENSOR_COUNTER` / `SENSOR_DETECTOR` / `ACCEL_ALGORITHM` / `MANUAL` / `UNAVAILABLE`。`ACCEL_ALGORITHM` 为算法估算，精度低于系统计步器 |
| `trackPoints.encoding` | `array` 表示紧凑数组编码；`object` 表示每个点是一个完整对象（可读性更好，体积更大） |
| `timestamp` | 一律使用 **Unix 毫秒时间戳**；人类可读时间（如 `startTime`）使用 ISO 8601 带时区 |
| `type` | 标记类型枚举：`SUMMIT` / `ALERT_DISTANCE` / `ALERT_ASCENT` / `ALERT_DESCENT` / `MANUAL`。未知类型解析时应忽略而非报错（向前兼容） |
| `difficulty` | 线路难度枚举：`EASY` / `MODERATE` / `HARD` / `CHALLENGING`。**存枚举、不存译文**——界面按枚举值 + 当前语言本地化渲染 |
| `crsNote` / `altitudeSourceNote` / `stepSourceNote` | **人可读的说明文本**，按导出时的 App 语言生成（与 `README.txt` 同一规则，见 `F-I18N-52`）。**解析时一律忽略**——程序只认对应的枚举字段，否则切语言后旧文件会残留旧语言 |
| `marker.label` | **仅用于人眼阅读**的展示文本（导出时按当时的 App 语言生成的快照）。**App 渲染标记时必须根据 `type` + 结构化数值本地化生成，不得直接使用此字段**——否则切换语言后旧记录会残留旧语言文本。唯一的例外是 `MANUAL` 类型：其 `label` 是用户输入原文，任何语言下都原样保留、不翻译 |
| `hasBarometer` | 可选。本次记录设备是否具备气压计；导入端据此还原海拔数据的可信度上下文 |
| `legs[].durationSec` | 该段起止墙钟时间差，**含该段内暂停**；两段之和与 `movingDurationSec` 的差即段间暂停等非运动时间 |
| `splits.byAltitudeGain[].paceSecPerKm` | 段内运动秒数 ÷（段距离 / 1000）；段距离 < 50 m 时写 `null`（与 byKilometer 同规则） |
| 空值约定 | 步数不可用沿用历史哨兵值 `-1`（见 6.5.2 口径表）；其余派生数值字段（配速、卡路里等）一律用 `null`——两类写法不得混用 |
| `uri` | 媒体文件仅存**引用**，不内嵌二进制；如需携带原文件，另提供「包含媒体文件」导出选项（zip） |
| `schemaVersion` | 遵循语义化版本；主版本号变化表示不兼容 |

**向后兼容约定**

1. 解析器必须**忽略未知字段**，不得因多出字段而失败
2. 新增字段一律可选，不得设为必填
3. 删除字段需提升主版本号
4. 枚举值新增时，旧版本解析器应降级为「未知类型」而非崩溃

**计划线路单文件导出（`F-PLAN-43`）**

计划线路单独导出时，复用上文 `plannedRoute` 对象的结构，外层套与单条记录相同的信封（7.4 的 `planned_routes/<route-id>.json` 即此格式）：

```json
  "plannedRoute": { "id": "pr-001", "name": "...", "source": "AUTO", "legs": [ "...同 7.3 plannedRoute.legs..." ] }

```

### 7.4 ZIP 备份包结构

```
GoHiking_Backup_20260919_165800.zip
├── manifest.json                 必须。备份元信息与文件清单
├── settings.json                 可选。用户设置
├── trips/                        运动记录，一条记录一个文件
│   ├── <trip-id>.json
│   └── ...
├── planned_routes/               计划线路，一条一个文件
│   ├── <route-id>.json
│   └── ...
├── media/                        可选。媒体原文件（默认不含）
│   ├── IMG_20260919_081320.jpg
│   └── VID_20260919_094500.mp4
└── README.txt                    人可读说明：格式、坐标系、字段含义
```

**`trips/` 下每个文件的内容 = 7.3 节定义的单个 trip JSON**。也就是说，**从 ZIP 里解出一个文件，就是一个可直接分享的单条 JSON**；反过来，一个单条 JSON 也能直接塞进 `trips/` 目录构成合法备份。两种格式共用同一套 schema 与解析器。

#### 为什么一条记录一个文件，而不是塞成一个大 JSON

| 理由 | 说明 |
| --- | --- |
| **流式导入** | 逐条解析、逐条入库，内存占用与记录总数无关。1000 条记录也不会 OOM |
| **故障隔离** | 单条记录损坏不影响其他记录导入 |
| **部分恢复** | 用户可以只解压、只导入自己需要的那几条 |
| **diff 友好** | Git、Beyond Compare 等工具能直接看出哪条记录变了 |
| **可读性** | 用户解压后能直观看到「我导出了 42 条记录」 |

| `schema` | 固定为 `gohiking.backup`，用于识别文件类型（与单条记录的 `gohiking.trip` 区分） |
| `schemaVersion` | **备份包格式版本**，与单条记录的 `schemaVersion` 独立演进 |
| `counts` | 声明数量。导入时与实际解出的数量比对，不一致则告警（可能是导出中断或文件被篡改） |
| `options.containsMedia` | 是否含媒体原文件，决定导入时要不要去 `media/` 找 |
| `checksums` | 逐文件 SHA-256。可关闭；开启时导入会校验，不匹配则跳过该文件并计入失败报告 |

#### README.txt 内容要求

包里必须放一份人可读的说明，让用户和第三方工具都能自己搞懂数据：

- 数据来源与**坐标系**说明（GCJ-02 / WGS-84）
- 各目录与文件的作用
- `trackPoints` 的**紧凑数组编码**说明（`fields` 数组与 `values` 的字段顺序对应关系）
- `altitudeSource` / `stepSource` 枚举值的含义与精度差异
- 开源仓库地址与 schema 文档链接
- 免责说明：本文件为个人运动数据，不含任何账号或设备标识

#### `settings.json` 的导入行为

`settings.json` 是**备份**的一部分，但导入时**默认不生效**（`F-IO-36`）：

| 场景 | 行为 |
| --- | --- |
| 默认 | 只导入记录与计划线路，**本机设置保持不变** |
| 用户主动勾选「同时恢复备份中的设置」 | 先展示**将改变的设置项清单**（只列与原值不同的项），二次确认后才写入 |
| 语言设置 `app_language` | **始终不导入**（`F-IO-37`）—— 语言是设备偏好；且 `AppCompatDelegate.setApplicationLocales` 会触发界面重建，放在导入流程里会掩盖导入结果 |
| 阈值类设置 | 导入后仍须过 `F-ALERT-12` / `F-ALERT-22` 的范围校验 |

> **为什么默认不导入设置**：设置是**设备偏好**，不是**数据资产**。用户导入数据最常见的场景是「换手机 / 补数据」，此时把旧设备的阈值、开关一并盖过来，往往是反直觉的。默认不动、需要时显式勾选，比默认覆盖安全得多。

### 7.5 导入兼容性规则

导入是**向前兼容**的：新版本 App 必须能读懂旧版本导出的文件。

| 场景 | 行为 |
| --- | --- |
| `schemaVersion` 主版本**相同** | 直接导入 |
| 导入文件主版本 **>** App 支持 | **拒绝**，提示「此文件由更新版本的 GoHiking 导出，请升级 App」 |
| 导入文件主版本 **<** App 支持 | 自动执行迁移链（逐版本升级到当前 schema） |
| 出现**未知字段** | 忽略，不报错、不中断 |
| **缺失可选字段** | 使用默认值填充 |
| **未知 `marker.type`** | 降级为「未知标记」展示，**保留原始值不丢弃** |
| `checksum` 不匹配 | 跳过该文件，计入失败报告，继续处理其他文件 |
| 声明的 `counts` 与实际不符 | 告警提示，但仍导入实际解出的内容 |
| 文件 `crs` 与内部（GCJ-02）不一致 | 自动转换后入库，转换前告知用户 |
| 文件**缺少** `crs` 字段 | 按 WGS-84 处理，并提示用户确认（老文件可能没有此字段） |
| ZIP 内缺少 `manifest.json` | 尝试按目录结构推断；推断失败则拒绝并说明原因 |
| ZIP 内混有非 GoHiking 文件 | 忽略，只处理符合 schema 的文件 |

### 9.6 可靠性与异常处理

| 场景 | 处理 |
| --- | --- |
| 定位信号丢失 | 轨迹断开，不产生跳变直线；恢复后新建 segment |
| 定位漂移 | 精度 > 50m 的点标记低质量，不参与统计 |
| GPS 长时间无信号（隧道/峡谷） | 界面提示「正在搜索卫星」，不中断记录 |
| App 崩溃 | 未结束的记录可恢复（每 10 秒持久化一次状态） |
| 存储空间不足 | 提示用户，暂停写入并保留内存数据 |
| 高德 SDK 初始化失败 | 提示 Key 配置问题，地图区降级为占位提示，记录功能仍可用 |
| TTS 不可用 | 静默降级，只打点 |
| **设备无气压计** | 自动降级为 GPS 估算模式（见 4.4.2），界面标注「GPS 估算」，海拔阈值下限提到 30m |
| **设备无计步传感器** | 自动降级到加速度计自研算法，提示耗电增加；算法也不可用则显示「—」并允许手动补录（见 4.5.3） |
| **记录中设备重启** | `TYPE_STEP_COUNTER` 归零 → 检测到计数器回退，标记该段步数无效并提示 |
| 权限被拒 | 逐项说明影响，提供跳转设置的引导 |
| **导入的 ZIP 含路径穿越条目**（`../`、绝对路径） | 拒绝该条目并计入失败报告，**不写出任何文件**（见 `F-IO-60`） |
| **导入的 ZIP 疑似 Zip Bomb** | 解压前校验声明的解压后总大小与条目数，超限（2 GB / 10000 条）直接拒绝并说明原因（见 `F-IO-61`） |
| **导入中途存储空间不足** | 回滚当前条目，保留已成功导入的记录，在结果报告中列为失败（见 `F-IO-65`） |
| **导入文件校验和不匹配** | 跳过该文件，计入失败报告，继续处理其余文件（见 7.5） |
| **导入文件 `schemaVersion` 主版本过高** | 拒绝并提示「请升级 GoHiking」，不尝试解析 |
| **高程数据源不可用** | 长按查海拔只显示经纬度、海拔显示「—」；计划线路爬升标注为不可用，**不编造数值**（见 6.1） |

### 9.7 国际化（i18n）

> **产品原则：中英双语是一等公民，不是「以后再说」。** 所有文案从第一天起就走资源文件——任何硬编码文案一律视为 Bug，不是「待优化项」。

#### 9.7.1 支持的语言与资源目录

| 语言 | 资源目录 | 状态 |
| --- | --- | --- |
| 英文（默认 / 兜底） | `res/values/strings.xml` | v1.0 必须 |
| 简体中文 | `res/values-zh-rCN/strings.xml` | v1.0 必须 |
| 繁體中文 | `res/values-zh-rTW/strings.xml` | v1.x 可选 |

**为什么默认目录放英文**：`res/values/` 是所有未匹配 locale 的**兜底目录**。把英文放这里，任何非中文用户至少能看到英文；如果把中文放默认目录，一个法语用户会看到满屏中文。

**Android 13+ 系统级 per-app 语言**：在 `res/xml/locales_config.xml` 声明支持的 locale，并在 `AndroidManifest.xml` 的 `<application android:localeConfig="@xml/locales_config">` 引用，用户就能在**系统设置**里单独给本 App 切语言，无需进 App。

```xml
<locale-config xmlns:android="http://schemas.android.com/apk/res/android">
    <locale android:name="en"/>
    <locale android:name="zh-CN"/>
</locale-config>
```

#### 9.7.2 字符串资源的组织

项目是多模块的（`core/*` + `feature/*`），多模块字符串管理有三个坑：

1. **重名冲突**——不同模块定义同名 string，资源合并时 app 模块**静默覆盖**，文案会莫名其妙变了，极难排查
2. **翻译分散**——翻译者要在十几个模块里翻找，必然漏
3. **无法整体校验**——没法一眼看出哪些文案还没翻译

**方案：集中放在 `core/resources` 模块，按功能域拆成多个 XML 文件。**

```
core/resources/src/main/res/
├── values/                        ← 英文（默认）
│   ├── strings_common.xml         通用：确定/取消/保存/删除/重试…
│   ├── strings_map.xml            F-MAP
│   ├── strings_plan.xml           F-PLAN
│   ├── strings_record.xml         F-REC
│   ├── strings_media.xml          F-MEDIA
│   ├── strings_history.xml        F-HIS
│   ├── strings_alert.xml          F-ALERT
│   ├── strings_settings.xml       F-SET
│   ├── strings_io.xml             F-IO
│   ├── strings_error.xml          所有错误与提示
│   ├── strings_tts.xml            语音播报文案（与显示文案分开）
│   ├── plurals.xml                复数形式
│   └── arrays.xml                 数组型文案
└── values-zh-rCN/                 ← 简体中文（文件名与英文侧一一对应）
    └── ...
```

**命名规范：`<域>_<对象>_<用途>`**，全小写下划线。

| 示例 | 说明 |
| --- | --- |
| `common_action_confirm` | 通用动作 |
| `record_stat_distance` | 记录页统计项 |
| `record_btn_summit` | 记录页按钮 |
| `error_gps_unavailable` | 错误文案 |
| `tts_alert_ascent` | 语音播报文案 |

> **为什么 `strings_tts.xml` 要单独一套**：语音播报和屏幕显示的**文案格式不同**。屏幕上显示「↑300m」，播报要念「已爬升 300 米，当前海拔 856 米」。硬用同一份资源，TTS 会念出「上箭头三百米」这种废话。

#### 9.7.3 格式化规范（最容易出 Bug 的地方）

| 规范 | 说明 |
| --- | --- |
| **必须用带位置的占位符** | `%1$s` `%2$d`，**禁止**裸 `%s` `%d` |
| **禁止字符串拼接** | 不要 `getString(a) + getString(b)`，用一条带占位符的完整文案 |
| **数字用 `NumberFormat`** | 处理千分位与小数点符号 |
| **日期用带 `Locale` 的格式化 API** | 中文 `2026-09-19 16:58` / 英文 `Sep 19, 2026 4:58 PM` |
| **复数用 `<plurals>`** | 英文有单复数（1 step / 2 steps），中文虽无变化也走 plurals，保证结构一致 |
| **单位走资源** | 不硬编码「公里」「km」，走 `unit_km` 之类的资源项 |

**为什么必须带位置**——这是最经典的 i18n Bug：

```xml
<!-- ❌ 错误：不带位置的占位符，翻译时无法调整语序 -->
<string name="plan_summary">%s 出发，%s 到达</string>

<!-- ✅ 正确：翻译者可以自由调整语序 -->
<string name="plan_summary">%1$s 出发，%2$s 到达</string>
<!-- 英文可译为：Departs %1$s, arrives %2$s
     也可以译为：Arrival %2$s, departure %1$s  ← 语序调换，参数不串位 -->
```

#### 9.7.4 不翻译的内容（明确边界）

| 内容 | 处理 |
| --- | --- |
| 代码注释、日志、异常堆栈 | 不翻译（开发者语言，统一英文） |
| JSON 字段名、schema 枚举值 | 不翻译（`BAROMETER_FUSED`、`MODERATE` 等是**协议**，不是文案） |
| 坐标系名称 | 不翻译（`GCJ-02` / `WGS-84`） |
| 单位符号 | `km` / `m` / `°` 用符号；「公里」「米」走资源 |
| **高德 POI 名称** | **由地图数据决定，不翻译**（见 9.7.7） |
| 用户输入内容（记录名、备注） | 不翻译 |
| 导出文件里的 `id`、`uri` | 不翻译 |
| 导出文件里的 `*Note` 说明文本 | **随导出时的 App 语言生成**（人可读说明；程序解析时忽略，与 `README.txt` 同规则，见 `F-I18N-52`） |
| 难度等级 | 存枚举 `MODERATE`，界面按语言渲染「中等 / Moderate」 |

#### 9.7.5 语言切换

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-I18N-10 | 默认跟随系统语言 | P0 |
| F-I18N-11 | 设置页提供手动切换：跟随系统 / 简体中文 / English | P1 |
| F-I18N-12 | 切换后**立即生效**，无需重启 App | P1 |
| F-I18N-13 | 选择持久化，重启后保持 | P1 |
| F-I18N-14 | Android 13+ 通过 `locales_config.xml` 支持系统级 per-app 语言设置 | P1 |

**实现要点**：使用 `AppCompatDelegate.setApplicationLocales(LocaleListCompat.forLanguageTags("zh-CN"))`。API 33+ 由系统接管持久化，低版本由 AppCompat 自己存。

> **不要手动修改 `Configuration`**——会导致资源不刷新、Activity 重建异常、Fragment 状态丢失。

#### 9.7.6 长度膨胀与布局（英文比中文长）

英文文案通常比中文**长 30–50%**（按字符数），德语可达 100%。必须提前防布局炸裂：

| 位置 | 风险 | 对策 |
| --- | --- | --- |
| 按钮 | 中文「登顶」2 字 → 英文 `Summit` 6 字符 | 用 `wrap_content`，**不写死宽度** |
| 底部 Tab | 「地图/计划/记录/我的」→ `Map / Plan / History / Me` | 均分宽度，`maxLines=1` + `ellipsize` |
| 数据面板 | 「累计爬升」→ `Total ascent` | 预留宽度或 `autoSizeTextType` |
| 设置项 | 「备份包含媒体文件」→ `Include media in backup` | 标题可换行，副标题独立成行 |
| 对话框 | 长英文可能挤爆标题栏 | `maxLines=2` |

**验收要求**：英文模式下**不允许出现文字截断、按钮撑破、文字重叠**。

#### 9.7.7 地图与语音的特殊处理

**地图标注语言**

高德 Android 地图 SDK 提供 `AMap.setMapLanguage(String language)`，支持中文与英文地图标注。

**但有一个必须实测的限制**：

- 高德官方说明为「**2D 地图 SDK** 支持展示国内英文地图」，本项目使用的是 **3D 地图 SDK**，是否同样生效**必须实测验证**（列入 M0 验证项）
- 英文标注的**覆盖范围有限**，可能只在大城市与主要路网生效；山区、乡村、小地名仍为中文
- 海外区域的标注语言不受此设置影响

> **结论：地图标注语言「尽力而为」，不承诺完全英文化。** 英文模式下地图上出现中文地名是可接受的，但必须在文档与 UI 中说明，不能让用户误以为是 App 的 Bug。

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-I18N-20 | App 语言切换时同步调用 `setMapLanguage` 切换地图标注语言 | P1 |
| F-I18N-21 | 英文模式下地图标注仍为中文时不报错、不提示异常（属数据源限制） | P0 |
| F-I18N-22 | 用户自建的地名（记录名、计划线路名）任何语言下都保持原样，不翻译 | P0 |

**语音播报（TTS）**

| 编号 | 需求 | 优先级 |

| F-I18N-30 | TTS 引擎按当前 App 语言设置 `Locale`（中文 `SIMPLIFIED_CHINESE` / 英文 `US`） | P1 |

## 12. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
| --- | --- | --- | --- |
| 高德无「登山/徒步」路径规划 | 推荐线路不符合登山场景 | 高 | 用步行规划 + 自建爬升评估排序；无路网时强制走手动打点兜底 |
| 国产 ROM 杀后台 | 记录中断，数据丢失 | 高 | 前台服务 + 电池白名单引导 + 每 10 秒持久化 + 崩溃恢复 |
| GPS 海拔不准 | 爬升统计失真 | 高 | 气压计融合 + 中值滤波 + 阈值法统计 |
